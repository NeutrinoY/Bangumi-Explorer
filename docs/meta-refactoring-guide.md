# 元技术重构指南

本文档用于指导 Agent 在本项目中进行深度重构时的思考方式、协作规则、权限边界和验证标准。

它不是具体的重构计划，不规定最终目录结构、技术选型、组件拆分、状态管理方案或代码实现方式。它的目标是建立一套稳定的重构协作协议，尽可能减少项目所有者与 Agent 在重构过程中的沟通成本，同时避免“只整理代码”和“失控改版”这两个极端。

## 1. 核心定位

本次重构的目标不是简单地移动文件、重命名组件或清理表面代码，而是系统性提升项目的长期质量。

重构应关注：

- 架构清晰度
- 模块边界
- 数据流可理解性
- 组件职责
- 样式组织
- 状态管理稳定性
- 可维护性
- 可扩展性
- 可测试性
- 用户体验一致性

同时，本项目的前端界面当前从用户视角可能已经基本可用。因此，重构不能把用户正在依赖的产品体验当作可以随意替换的实现细节。

本指南的核心原则是：

> 架构层面允许大胆重构，体验层面默认保持等价，缺陷层面允许修复，产品层面必须确认。

## 2. 重构不是产品改版

Agent 必须明确区分以下三类工作：

- 重构：改变内部实现，提升结构质量，尽量不改变用户可感知体验。
- 缺陷修复：修复现有不合理、不稳定、不一致或明显错误的行为。
- 产品改版：改变用户路径、信息架构、核心视觉风格、业务语义或功能范围。

本指南允许 Agent 在重构过程中主动发现并修复问题，也允许 Agent 提出更好的设计、交互和视觉优化方向。

但除非得到明确授权，否则 Agent 不应把产品改版混入架构重构。

## 3. 用户视角下的“不变”

“用户视角下的前端样式和交互体验不变”不表示代码不变、DOM 不变、CSS 类名不变或组件层级不变。

它表示：

> 在相同数据、相同浏览器尺寸、相同用户操作路径下，重构前后的页面视觉布局、可见内容、交互路径、状态反馈、响应式表现、默认行为和错误处理应保持等价。

### 3.1 视觉等价

默认应保持：

- 页面整体布局
- 视觉层级
- 字体大小和字重
- 颜色语义
- 间距密度
- 卡片、按钮、表单、列表、弹窗等控件形态
- 图标尺寸和相对位置
- hover、active、disabled、focus 等状态
- loading、empty、error、success 等状态表现
- 桌面端、平板端和移动端响应式布局

视觉等价不要求像素级冻结，但应达到：

> 老用户不会认为产品被重新设计，新用户看不出重构痕迹。

### 3.2 交互等价

默认应保持：

- 主要操作路径
- 按钮位置和用途
- 点击、输入、筛选、排序、分页、搜索等行为
- 弹窗、抽屉、菜单、提示等组件的打开和关闭方式
- 表单校验时机
- 提交、成功、失败和撤销反馈
- 页面跳转行为
- 浏览器返回、刷新后的状态表现
- 键盘操作和焦点顺序

功能仍然存在不等于体验不变。如果入口变化、步骤增加、反馈消失或状态保留方式改变，都属于用户可感知变化。

### 3.3 信息等价

默认应保持：

- 页面标题
- 分区结构
- 信息优先级
- 字段顺序
- 默认排序
- 默认筛选
- 默认分页策略
- 文案含义
- 占位符和提示语
- 空状态和错误状态信息

很多重构风险来自“看起来差不多，但默认状态变了”。Agent 必须特别注意这类隐性变化。

### 3.4 行为语义等价

默认应保持用户对系统的心智模型。

例如：

- 原本点击条目进入详情页，重构后不应擅自改成展开面板。
- 原本筛选条件会保留，重构后不应刷新即丢失。
- 原本搜索会即时响应，重构后不应改成必须按回车。
- 原本错误后保留用户输入，重构后不应清空表单。
- 原本不可点击按钮有明确灰态，重构后不应变成可点击但报错。

用户依赖的隐性规则同样属于产品体验的一部分。

## 4. Agent 的自主权边界

Agent 不是只能机械复刻现状。高质量重构要求 Agent 能够主动识别旧系统中的问题，并在合适的权限范围内修正或提出改进。

但 Agent 的自主权必须分层管理。

### 4.1 可以直接执行的改动

以下改动通常可以直接执行，但必须在阶段总结或变更记录中说明：

- 内部架构调整
- 目录结构整理
- 组件职责拆分
- 重复逻辑收敛
- 数据流简化
- 状态管理整理
- 类型定义完善
- 明显 bug 修复
- 明显布局溢出修复
- 图标、文字、控件轻微错位修复
- 移动端明显适配问题修复
- loading 抖动修复
- 状态闪烁修复
- 控制台错误修复
- 重复请求或竞态问题修复
- hover、active、disabled、focus 状态补全
- loading、empty、error 状态补全
- 可访问性属性补全
- 不改变视觉意图的样式一致性修复
- 不改变产品语义的性能优化

这些改动的共同特征是：

> 用户即使感知到变化，也更可能认为它“终于正常了”，而不是“产品改版了”。

### 4.2 需要先提出再执行的改动

以下改动可能是正确方向，但必须先提出方案并等待确认：

- 改变页面整体结构
- 调整主要导航
- 调整核心信息层级
- 改变主要操作路径
- 改变默认排序
- 改变默认筛选
- 改变分页或加载策略
- 改变搜索触发方式
- 改变表单校验时机
- 改变弹窗、抽屉、页面之间的承载方式
- 移动关键按钮位置
- 重写核心文案
- 改变页面密度
- 改变主要视觉风格
- 新增核心功能
- 删除或合并现有功能
- 改变业务语义

这些改动的共同特征是：

> 用户可能需要重新理解或重新适应产品。

### 4.3 只应记录为未来方向的改动

以下内容通常不应混入本次重构，除非项目所有者明确批准：

- 全新设计系统
- 全面视觉改版
- 品牌风格重塑
- 信息架构重做
- 大规模交互模式重做
- 新产品功能规划
- 业务流程再设计
- 非必要技术栈迁移

Agent 可以把这些内容记录为“未来建议”，但不应在重构中顺手实施。

## 5. 变化分级

所有用户可见变化都应被归类。推荐使用以下分级：

### 5.1 equivalent

等价重构。

用户不可感知，或理论上不应感知。只改变内部实现。

示例：

- 拆分组件但页面不变
- 合并重复逻辑
- 改善类型定义
- 调整内部数据转换位置
- 替换实现方式但输出一致

### 5.2 fix

缺陷修复。

用户可能感知到变化，但该变化修复了现有错误、不稳定或明显不合理之处。

示例：

- 修复移动端溢出
- 修复按钮 disabled 状态缺失
- 修复重复请求导致的闪烁
- 修复加载状态不一致
- 修复控制台错误
- 修复错误后输入丢失

### 5.3 enhancement

体验增强。

改动可能提升体验，但并非显然的缺陷修复。通常需要说明理由，低风险时可以纳入当前阶段，高影响时需要确认。

示例：

- 统一同类控件的交互反馈
- 优化空状态表达
- 改善局部信息呈现
- 优化局部响应式布局
- 减少不必要的视觉噪音

### 5.4 product-change

产品变更。

改变用户路径、产品语义、信息架构、核心视觉风格或功能范围。必须等待确认。

示例：

- 改默认排序
- 改导航结构
- 改主要页面布局
- 改核心文案风格
- 删除功能
- 新增核心功能
- 改详情页承载方式

## 6. 重构前的体验基线

在进行实质性重构前，Agent 应尽可能建立当前项目的体验基线。

体验基线不是为了阻止改进，而是为了让改进可审计、可比较、可回退。

### 6.1 基线内容

建议至少记录：

- 关键页面清单
- 关键用户路径
- 关键交互点
- 当前路由结构
- 当前核心状态
- normal 状态截图
- loading 状态截图或说明
- empty 状态截图或说明
- error 状态截图或说明
- 桌面端表现
- 移动端表现
- 已知明显问题
- 可接受变化
- 不可接受变化

### 6.2 基线判断标准

Agent 应关注：

- 用户第一眼看到什么
- 用户主要任务如何完成
- 页面默认展示什么
- 异步数据如何反馈
- 错误如何反馈
- 空数据如何反馈
- 操作后状态是否保留
- 刷新后状态是否保留
- 返回后状态是否保留
- 移动端是否仍然可用

## 7. 推荐工作流程

Agent 在开始重构时，推荐遵循以下顺序。

### 7.1 阶段一：项目诊断

先阅读项目，而不是直接设计理想架构。

诊断应包括：

- 技术栈
- 构建方式
- 路由方式
- 数据获取方式
- 状态管理方式
- 样式系统
- 组件组织
- 页面组织
- 公共工具
- 类型系统
- 测试和验证命令
- 主要风险点
- 当前体验问题

输出应避免直接给出未经验证的宏大方案。

### 7.2 阶段二：重构协议确认

在具体计划前，Agent 应确认本指南中的关键规则是否适用于当前项目。

如存在特殊情况，应明确提出：

- 哪些页面必须严格保持
- 哪些区域允许主动优化
- 哪些现有问题建议直接修复
- 哪些现有问题需要产品确认
- 哪些风险需要先建立验证手段

### 7.3 阶段三：分阶段计划

计划必须分阶段，且每个阶段都应保持项目可运行。

每个阶段应说明：

- 阶段目标
- 涉及范围
- 预计修改模块
- 不涉及范围
- 用户可见影响
- 风险
- 验证方式
- 完成标准

不得用“整体重构”“全面优化”“清理代码”等模糊表述替代可执行阶段。

### 7.4 阶段四：执行

执行时应遵循：

- 每次只做当前阶段范围内的改动
- 不顺手重构无关文件
- 编辑前说明将修改的区域
- 编辑后运行可用验证
- 发现计划不适用时先说明并修订
- 遇到用户已有改动时不得擅自回滚
- 任何产品级变化都必须先确认

### 7.5 阶段五：阶段复盘

每个阶段结束后，Agent 应回答：

- 本阶段改了什么？
- 是否有用户可见变化？
- 哪些变化是 equivalent？
- 哪些变化是 fix？
- 哪些变化是 enhancement？
- 是否存在 product-change？
- 如何验证没有退化？
- 是否发现新的风险？
- 下一阶段计划是否需要调整？

## 8. 重构过程中的记录要求

为了降低沟通成本，Agent 应在重构过程中维护清晰记录。

这些记录不一定都要创建为独立文件，但至少应在阶段输出中可追踪。

### 8.1 UX_CHANGELOG

用于记录用户可见变化。

推荐字段：

- 位置
- 改动类型
- 是否用户可见
- 改动原因
- 影响范围
- 风险
- 是否需要确认
- 验证方式

示例：

```text
位置：搜索结果列表
类型：fix
是否用户可见：是
原因：移动端卡片标题在窄屏下溢出
影响范围：移动端列表展示
风险：低
是否需要确认：否
验证方式：移动端 viewport 截图
```

### 8.2 REFACTORING_NOTES

用于记录结构性决策。

推荐字段：

- 决策内容
- 背景问题
- 采用方案
- 放弃方案
- 权衡原因
- 影响范围
- 后续约束

### 8.3 RISK_REGISTER

用于记录风险。

推荐字段：

- 风险描述
- 触发条件
- 影响范围
- 严重程度
- 缓解方式
- 验证方式

### 8.4 DESIGN_OPPORTUNITIES

用于记录值得未来考虑的设计和交互改进。

推荐字段：

- 问题
- 建议
- 用户收益
- 工程收益
- 风险
- 是否适合本次重构
- 是否需要产品确认

## 9. 验证原则

重构不能只依赖“代码看起来更好”。必须尽可能通过可运行、可观察的方式验证。

### 9.1 基础验证

优先运行项目已有命令，例如：

- 类型检查
- lint
- 格式检查
- 单元测试
- 构建
- 本地运行

如果某些命令不存在，Agent 应说明缺口，而不是假装已经验证。

### 9.2 前端体验验证

对于涉及前端的重构，应尽可能验证：

- 关键页面能打开
- 关键路径能完成
- 主要交互能触发
- loading 状态合理
- empty 状态合理
- error 状态合理
- 桌面端布局无明显退化
- 移动端布局无明显退化
- 控制台无新增关键错误
- 网络请求无明显异常

### 9.3 截图验证

当样式或交互可能受影响时，推荐使用截图作为对照。

建议覆盖：

- 桌面端关键页面
- 移动端关键页面
- 核心交互前后状态
- 弹窗或菜单状态
- 空状态
- 错误状态

截图对比的目标不是强制像素一致，而是发现非预期退化。

### 9.4 验证失败处理

如果验证失败，Agent 应：

- 说明失败命令或失败路径
- 判断是否由本阶段改动引起
- 优先修复本阶段引入的问题
- 如果是既有问题，应记录并说明是否影响当前阶段
- 不得在未说明的情况下扩大改动范围

## 10. 设计和交互改进的处理方式

Agent 应主动识别更好的设计方向，但必须以可控方式处理。

### 10.1 可以直接纳入的改进

通常包括：

- 修复明显不一致
- 补齐缺失状态
- 修复响应式问题
- 提升反馈清晰度
- 提升焦点和键盘可用性
- 减少由性能问题造成的卡顿和闪烁
- 统一同类控件细节

这些改进不应改变产品意图。

### 10.2 需要确认的改进

通常包括：

- 改主要信息结构
- 改页面密度
- 改核心操作入口
- 改默认行为
- 改主视觉风格
- 改主要文案表达
- 改用户完成任务的路径

Agent 应先提出：

- 当前问题
- 建议方案
- 用户收益
- 工程收益
- 风险
- 替代方案
- 是否建议纳入本次重构

### 10.3 不应混入的改进

通常包括：

- 全面 redesign
- 新功能规划
- 品牌重塑
- 大范围信息架构变化
- 非必要技术迁移

这些可以进入未来建议，不应阻塞或污染当前重构。

## 11. 决策规则

当 Agent 不确定某个改动是否可以直接执行时，应使用以下判断。

### 11.1 用户感知判断

问：

- 用户是否会注意到？
- 用户是否需要重新学习？
- 用户是否会觉得入口变了？
- 用户是否会觉得默认结果变了？
- 用户是否会觉得视觉风格变了？

如果答案大概率为是，应先提出。

### 11.2 产品语义判断

问：

- 是否改变了这个功能“是什么”？
- 是否改变了这个功能“如何使用”？
- 是否改变了数据被解释的方式？
- 是否改变了成功和失败的含义？
- 是否改变了默认业务规则？

如果答案为是，应先确认。

### 11.3 缺陷修复判断

问：

- 当前行为是否明显错误？
- 当前行为是否与同类组件不一致？
- 当前行为是否导致用户无法完成任务？
- 当前行为是否导致信息不可读、不可点或不可访问？
- 当前行为是否产生控制台错误或状态竞态？

如果答案为是，通常可以作为 fix 直接处理。

### 11.4 可回退判断

问：

- 改动是否局部？
- 是否容易还原？
- 是否有明确验证方式？
- 是否不会牵连核心路径？

如果答案为否，应降低自主执行级别。

## 12. 沟通协议

为了减少沟通成本，Agent 的沟通应遵循以下规则。

### 12.1 不要过早提方案

在没有阅读项目之前，不应直接提出完整重构方案。

优先顺序应为：

1. 理解项目
2. 建立基线
3. 识别风险
4. 提出计划
5. 分阶段执行

### 12.2 不要用空泛词汇

应避免只说：

- 优化代码结构
- 提升可维护性
- 清理逻辑
- 重构组件
- 改善体验

应具体说明：

- 哪个模块
- 什么问题
- 为什么是问题
- 怎么改
- 有什么风险
- 如何验证

### 12.3 默认继续推进

除非遇到产品级决策、重大风险或不可恢复操作，Agent 应基于本指南做合理判断并继续推进。

不应因为每个微小选择都询问项目所有者而制造额外沟通成本。

### 12.4 需要询问的场景

以下情况必须询问：

- 改动会改变核心用户路径
- 改动会改变默认业务行为
- 改动会改变主要视觉风格
- 改动会删除功能
- 改动会引入新功能
- 改动会改变路由语义
- 改动会大幅扩大阶段范围
- 验证结果显示存在重大退化

### 12.5 汇报格式

阶段汇报应优先包含：

- 已完成事项
- 验证结果
- 用户可见变化
- 风险和遗留问题
- 下一步建议

避免把大量内部过程当成主要内容，除非这些过程影响决策。

## 13. 代码质量标准

重构不能只追求“看起来更整齐”。高质量代码应在当前项目规模、产品定位和未来维护方式下，用合理的复杂度清楚表达业务意图，并让后续修改不容易误伤。

本项目是个人番剧收藏展览 Web 网页，不是大型多人 SaaS 或企业后台系统。因此，代码质量目标应偏向：

- 轻量
- 直接
- 清晰
- 稳定
- 可测试
- 低维护成本
- 与用户体验一致

不应为了“架构感”引入超过项目需要的复杂度。

### 13.1 正确性

代码首先必须做对事。

Agent 在重构时应关注：

- 功能结果是否正确
- 边界条件是否正确
- 异常情况是否正确
- 异步状态是否正确
- 数据为空时是否稳定
- 数据缺字段时是否稳定
- 网络失败时是否稳定
- 用户重复点击或快速切换时是否稳定
- 刷新、返回、重新进入页面时状态是否合理

优雅但不可靠的代码不是高质量代码。

### 13.2 可读性

代码应让未来维护者能够快速理解：

- 这个模块负责什么
- 这个状态从哪里来
- 这个函数为什么存在
- 这个判断对应什么业务规则
- 这个组件为什么这样拆
- 修改某个功能应该去哪一层

可读性要求：

- 命名清楚
- 结构直观
- 分支逻辑不绕
- 文件长度适中
- 注释解释必要背景，而不是重复代码字面含义
- 不滥用技巧性写法
- 不依赖过多隐式约定

复杂代码可以存在，但复杂度必须来自真实业务，而不是来自表达方式本身。

### 13.3 职责边界

职责分明是本项目重构时最重要的代码质量目标之一。

原则上：

- 页面负责组合，不负责承载大量业务细节。
- UI 组件负责展示和触发事件，不隐藏复杂业务规则。
- 领域逻辑应尽量是纯函数，不依赖浏览器、网络或具体 UI。
- hook 负责连接副作用，例如 URL、Supabase、fetch、事件监听和浏览器状态。
- 数据访问不应散落在展示组件中。
- 配置和常量应有明确归属。

一个模块最好能用一句话说明职责。如果一个文件同时管理数据、UI、URL、权限、业务规则和副作用，通常说明边界需要重新审视。

### 13.4 简洁性

简洁不是代码行数最少，而是没有不必要的结构、重复和绕路表达。

应避免：

- 无意义包装
- 过早抽象
- 不必要依赖
- 把简单问题工程化
- 为了 DRY 强行合并不同语义
- 为每个微小 UI 元素创建过度独立的抽象
- 为了显示“架构高级”增加层级

应追求：

- 默认值集中
- 规则集中
- 状态流向清楚
- API 面小
- 文件职责明确
- 重复只在语义相同时消除

好的精炼是减少冗余；坏的精炼是压缩语义。

### 13.5 可维护性

代码应让需求变化时的修改成本保持合理。

好的可维护性表现为：

- 改一个需求只影响少数显然相关的位置
- 新增规则有明确位置
- 删除功能不会牵连大量无关模块
- 技术债可以识别
- 技术债可以局部处理
- 抽象能减少真实复杂度
- 文件和模块之间没有隐性强耦合

如果新增一个筛选条件、排序方式、收藏状态或展示模式需要修改大量无关文件，说明代码边界可能存在问题。

### 13.6 可测试性

重构后的关键逻辑应尽可能容易被验证。

适合优先测试的内容包括：

- 筛选逻辑
- 排序逻辑
- 分页逻辑
- URL 解析和序列化
- 收藏状态转换
- 权限判断
- 数据清洗
- ETL 转换
- 边界输入
- bug 修复对应的回归场景

提高可测试性的方式：

- 把核心规则写成纯函数
- 把副作用隔离在 hook、adapter 或边界层
- 减少对全局状态和浏览器环境的直接依赖
- 避免让测试脆弱地绑定 DOM 细节或组件内部实现

不可测试的代码不必然错误，但长期风险更高。

### 13.7 一致性

同类问题应使用同类方式解决。

应保持一致的内容包括：

- 命名风格
- 文件组织
- 组件 API 风格
- 错误处理方式
- 状态命名方式
- 样式组织方式
- 数据转换位置
- 配置定义位置
- 测试组织方式

一致性能降低认知成本。个人项目同样需要一致性，因为未来维护者很可能就是几个月后的项目所有者或另一个 Agent。

### 13.8 单一事实来源

同一个概念应尽量只有一个权威定义。

需要特别注意：

- 默认筛选值
- 默认类型
- 分页大小
- 状态枚举
- 排序选项
- preset 配置
- 状态颜色
- URL 参数名
- 数据字段含义
- 权限相关常量

重复代码不总是问题，但“同一语义的重复”是问题。它会导致未来改一处忘一处。

### 13.9 类型质量

TypeScript 不应只是为了让编译器不报错，而应表达真实领域。

好的类型应做到：

- 领域对象边界清楚
- UI 状态和数据模型区分清楚
- 外部数据和内部可信数据区分清楚
- 无效状态尽量不能被轻易构造
- 不滥用 any
- 不用过宽类型掩盖问题
- 类型定义不重复散落
- API 返回值和业务状态有明确转换边界

如果外部数据来源不完全可信，应在数据进入核心逻辑前进行转换、默认值处理或校验。

### 13.10 鲁棒性

代码应能面对不理想输入和运行环境。

需要考虑：

- 数据格式异常
- 图片地址失效
- API 返回错误
- 网络超时
- 环境变量缺失
- 权限失效
- Supabase 写入失败
- 客户端和服务端环境差异
- 并发操作
- 快速连续点击
- 实时订阅重复触发

鲁棒性不是把所有错误都吞掉，而是让失败可控、可见、可恢复。

### 13.11 性能

性能优化应服务于真实体验，而不是盲目追求指标。

本项目应重点关注：

- 首屏可用速度
- 数据加载速度
- 筛选和排序耗时
- 大量卡片渲染成本
- 图片加载策略
- 动画流畅度
- 不必要重渲染
- bundle 体积
- 移动端性能

如果没有证据表明某处是瓶颈，不应为了性能引入明显更复杂的结构。

### 13.12 安全性

涉及 Supabase、管理员写入和公开访问时，必须保持基本安全边界。

Agent 应注意：

- 不把客户端判断当作真实安全边界
- RLS 才是写入权限的关键防线
- 环境变量使用边界清楚
- 管理员写入逻辑可审计
- 错误信息不过度暴露敏感信息
- 外部数据源和依赖保持可信

本项目不是高风险金融系统，但公开网页和私有写入并存时，安全边界仍然重要。

### 13.13 可演进性

好代码不需要预先支持所有未来，但不应堵死合理演进路径。

应考虑未来是否容易：

- 新增筛选条件
- 新增排序方式
- 新增收藏状态
- 新增展示模式
- 新增详情信息
- 新增数据源
- 替换后端服务
- 增加分享页面
- 增加更强的数据校验

可演进性应通过清晰边界和适度抽象获得，而不是通过提前建设庞大框架获得。

### 13.14 用户体验保护

前端代码质量不能只看源码，也要看用户实际感受。

代码重构后应保护：

- loading 状态
- empty 状态
- error 状态
- disabled 状态
- hover 和 focus 状态
- 移动端布局
- 用户输入
- 返回和刷新行为
- 状态切换稳定性
- 动画和交互流畅度

如果源码更干净但用户体验退化，这不是成功的重构。

### 13.15 与项目规模匹配

同一套写法在不同项目中质量评价不同。

对本项目而言，应优先选择：

- 小而清楚的模块
- 明确的领域函数
- 轻量的 hook
- 可复用但不过度泛化的组件
- 明确的配置对象
- 稳定的测试护栏

应谨慎引入：

- 企业级分层模板
- 复杂状态框架
- 过重的后端抽象
- 过度组件库化
- 大量泛型和元编程
- 为未来假设准备的复杂扩展点

代码应与项目真实规模匹配。复杂架构只有在它降低真实复杂度时才值得引入。

### 13.16 本项目推荐代码风格

本项目推荐采用以下总体风格：

> Functional core, imperative shell.

即：

- 核心规则使用纯函数表达。
- 外部连接放在 hook、adapter 或边界层。
- 页面负责组合。
- UI 组件负责展示。
- 副作用集中处理。
- 领域规则可测试。

更具体地说：

- 少写没有信息量的代码。
- 多写能表达业务事实的代码。
- 不追求最短代码。
- 不追求最多抽象。
- 不为了复用牺牲语义清晰。
- 不为了视觉不变而保留明显错误。
- 不为了重构而改变产品意图。

一句话总结：

> 好代码不是少，而是不多余；不是复杂，而是能承载复杂功能；不是抽象多，而是职责和意图清楚。

## 14. 重构质量标准

一次合格的深度重构应满足：

- 项目仍可运行
- 核心用户路径不退化
- 用户可见体验没有非预期改版
- 明显缺陷得到修复或记录
- 模块边界更清晰
- 数据流更可理解
- 组件职责更明确
- 样式组织更稳定
- 类型和接口更可信
- 未来修改成本降低
- 验证方式更明确

一次不合格的重构通常表现为：

- 目录变了但复杂度没有降低
- 抽象增加但理解成本更高
- 组件拆细但职责更混乱
- 样式被重写但体验退化
- 计划很宏大但无法阶段交付
- 功能还在但用户路径改变
- 修复一个问题引入多个隐性变化
- 没有验证就声称完成

## 15. 推荐给 Agent 的启动提示词

在正式开始重构时，可以使用以下提示词。

```text
我希望你作为高水平工程 Agent，协助我对本项目做一次深度重构。

本次重构的核心目标不是单纯改目录或清理代码，而是提升项目的长期可维护性、架构清晰度、体验一致性和后续扩展能力。

请遵循 docs/meta-refactoring-guide.md。

重要约束：
- 架构层面允许大胆重构。
- 用户体验层面默认保持等价。
- 明显缺陷可以直接修复并记录。
- 设计、交互和视觉优化可以主动提出。
- 改变产品意图、核心用户路径、默认行为或主要视觉风格前必须先确认。
- 不要把产品 redesign 混入架构重构。

请先不要改代码。

第一步请完整阅读项目结构和关键源码，产出重构诊断报告，包括：
1. 当前项目的技术结构
2. 用户可见功能和页面清单
3. 当前架构的主要问题
4. 当前体验层面的明显问题
5. 可以直接修复的问题
6. 需要确认的设计或交互改进
7. 主要风险
8. 建议的体验基线和验证方式
9. 分阶段重构方向

等我确认后，再进入具体阶段计划和执行。
```

## 16. 最终原则

本指南最终服务于一个目标：

> 让 Agent 在不频繁打断项目所有者的前提下，做出高质量、可验证、可审计、可持续推进的重构决策。

因此，Agent 应同时具备两种能力：

- 工程自主性：能主动发现问题、设计结构、推进实现、验证结果。
- 产品克制性：能识别哪些变化触及用户心智模型，并在必要时等待确认。

高质量重构不是把项目改得“看起来更高级”，而是让项目在保持产品连续性的同时，拥有更清晰、更稳固、更容易演进的内部结构。
